A
Why SQL / PostgreSQL?
The app's data model requires relational guarantees. These are not preferences — they are load-bearing.
ℹ
SQL (Structured Query Language) is the language used to talk to relational databases. PostgreSQL is a specific relational database — the most widely used open-source one. The key word is relational: data is stored in structured tables that can reference each other with enforced rules.

1. Four tables that depend on each other

The app has a strict chain: a Document (One-Pager) spawns a Pipeline Run, which produces a PRD Document, which contains up to 12 PRD Frames (one per section). Each step references the previous one by ID. PostgreSQL enforces these links — if you try to delete a Document that has an active Pipeline Run, the database blocks it. Without this, deleting a document could leave orphaned pipeline runs and incomplete PRDs with no parent to belong to.

-- From lib/db-migrations/002-prd-tables.sql (actual codebase)
CREATE TABLE pipeline_runs (
  source_document_id UUID REFERENCES documents(id),   -- must point to a real document
  status             TEXT CHECK (status IN ('running','awaiting_approval','approved','completed','failed'))
);
CREATE TABLE prd_frames (
  prd_document_id UUID REFERENCES prd_documents(id)  -- must point to a real PRD
);

2. The PRD pipeline is a state machine with enforced values

The 4-agent PRD pipeline (Analyst → Architect → Writer → QA) transitions through exactly five states. The human approval gate at Agent 2 reads this status to decide whether to proceed. PostgreSQL's CHECK constraint rejects any invalid status at write time — a typo or bug can't corrupt the pipeline state. Without this constraint, a crashed agent could write garbage and the human gate would never fire.

3. Version history requires atomic transactions

Every time a One-Pager is saved, the app does three things in sequence: read the current document, push its content into a version history array, then write the new content. All three must succeed or fail together — if the write fails after the snapshot was pushed, the history would contain a ghost entry. PostgreSQL wraps this in a transaction that rolls back automatically on any failure. This is what makes the admin rollback feature reliable.

4. Content guardrails use atomic counters

The ban system tracks how many guardrail violations a user has triggered. It uses a PostgreSQL ON CONFLICT upsert — a single atomic operation that either inserts a new ban record or increments the existing count. Without atomicity, two simultaneous violations could both read count=1 and both write count=2, permanently under-counting and missing a ban threshold.

-- From lib/db.ts (actual codebase)
INSERT INTO banned_users (user_id, violation_count)
VALUES ($1, 2)
ON CONFLICT (user_id) DO UPDATE SET
  violation_count = banned_users.violation_count + 1;  -- atomic increment

5. The PRD export reads 12 sections in guaranteed order

Building a DOCX/HTML export requires fetching all 12 PRD sections and assembling them in the correct order. The query sorts by section_order — a column that only makes sense in a relational, ordered result set. The export would silently produce wrong section sequences without this.

✓
Why PostgreSQL specifically? It's the most capable open-source relational database — supports JSONB (we store document content as structured JSON inside SQL rows), arrays, gen_random_uuid(), full-text search, and the pg npm driver that the codebase already uses. MySQL and SQLite are alternatives but lack JSONB and the ON CONFLICT syntax the codebase relies on.
B
Why did we choose Neon?
Neon was the fastest path from zero to a live PostgreSQL database — ideal for early development.

🚀 Zero setup

Neon is a serverless PostgreSQL service. Creating a database takes 30 seconds in a browser — no server provisioning, no instance sizing, no connection pooler to configure. For a project starting from scratch, this removes days of infrastructure work.

🔗 Vercel integration

The app was originally deployed on Vercel. Neon has a first-class Vercel integration — one click sets POSTGRES_URL in the Vercel dashboard automatically. The connection string just appears.

💸 Free tier

Neon's free tier covers a small database with no time limit. For R&D tooling with a handful of users, the cost was $0/month during development.

📦 Standard PostgreSQL

Neon is real PostgreSQL — same SQL syntax, same pg npm driver, same migration files. Switching away from Neon to any other PostgreSQL host requires changing exactly one line: the POSTGRES_URL connection string.

⚠
Why we're moving away from Neon: The company is migrating all infrastructure to GCP. Neon is a third-party service outside the GCP org — it can't use GCP Secret Manager, VPC networking, Cloud IAM, or Cloud Audit Logs. For a GCP-native deployment, Cloud SQL is the equivalent product that lives inside the org.
C
Why can't we use Firebase / Firestore?
Firebase is a NoSQL document store. The app's data model requires features that NoSQL fundamentally cannot provide.
🚫
Firebase/Firestore is a Google product, but it is a completely different type of database — NoSQL, document-based, schema-free. Switching to it would not be a configuration change. It would be a rewrite of the entire data layer — approximately 800 lines of query code across lib/db.ts, lib/prd-db.ts, and every API route that touches the database.
Requirement PostgreSQL Firebase / Firestore
Foreign keys (documents → pipeline_runs → prd_documents → prd_frames) ✓ Native, enforced at DB level ✗ Does not exist. Must enforce manually in app code.
Status constraint (pipeline states) ✓ CHECK constraint, DB rejects invalid values ✗ No schema constraints. Any value can be written.
ACID transactions (version history snapshot) ✓ Full transaction support, automatic rollback ⚠ Limited transactions (max 500 docs, extra cost per op)
Atomic upsert (ban counter) ✓ ON CONFLICT … DO UPDATE in one round trip ✗ Requires transaction + read + conditional write (3 round trips, race window)
Ordered cross-collection query (prd_frames by section_order) ✓ ORDER BY on any column, single query ✗ No joins across collections. Multiple fetches + manual sort in app code.
JSONB storage (document content_json) ✓ Native JSONB with indexing ⚠ Documents are JSON-like, but no SQL querying into the content
Soft deletes with timestamp (deleted_at) ✓ Simple nullable column ⚠ Possible but requires filtering every query manually
Existing migration files (001–003) ✓ Run as-is on Cloud SQL ✗ All three migrations are PostgreSQL DDL — incompatible
Code change required to migrate ✓ One line — change POSTGRES_URL ✗ Rewrite ~800 lines across 10+ files
ℹ
Firebase is excellent for the right use case — real-time sync, mobile apps, user-facing feeds. It's the wrong tool here because the app's data is deeply relational: a PRD doesn't make sense without its parent One-Pager, and 12 sections don't make sense without their parent PRD. That hierarchy needs enforcement, not hope.

E
How does Google Cloud SQL help us?
Cloud SQL is the managed PostgreSQL service inside GCP — everything Neon does, but native to the org.

🔐 Stays inside the GCP org

Cloud SQL runs inside r-and-d-489319 — the same GCP project as Cloud Run. Traffic between the app and the database never leaves Google's private network. No public internet, no external SaaS vendor, no data leaving the org boundary.

🔑 Uses Secret Manager for credentials

The POSTGRES_URL is stored as a GCP Secret Manager secret and injected into Cloud Run at deploy time. No credentials in environment files, no manually updated Vercel dashboard, no secrets visible in CI/CD logs.

🔌 Zero code changes

Cloud SQL speaks standard PostgreSQL. The app uses the pg npm driver. The only change is one environment variable — the connection string switches from Neon's TCP URL to Cloud SQL's Unix socket path. Every query, migration file, and type definition is unchanged.

# Before (Neon)
POSTGRES_URL=postgres://user:pass@neon-host/db

# After (Cloud SQL) — one line change
POSTGRES_URL=postgres://user:pass@/db?host=/cloudsql/PROJECT:REGION:INSTANCE

🛡 IAM-controlled access

Cloud SQL access is controlled by GCP IAM roles — the same system that controls everything else in the org. No separate user/password management needed for the Cloud Run service account. Access is granted once via roles/cloudsql.client and managed centrally.

📋 Audit logs

Every database connection and query can be logged to Cloud Audit Logs — the same audit trail used across all GCP services. Compliance, incident response, and access reviews all go through one system.

💾 Automated backups

Cloud SQL takes daily automated backups with point-in-time recovery — configurable retention up to 7 days. No manual pg_dump scripts, no cron jobs, no risk of forgetting to back up before a migration.

ℹ
The Auth Proxy advantage: Cloud Run connects to Cloud SQL through the Cloud SQL Auth Proxy — a sidecar that handles encryption and IAM authentication automatically. The app never needs to manage TLS certificates or rotate database passwords. The connection string uses a Unix socket path instead of a hostname.

Can we defer SQL? And can Google Drive replace it?
Two practical questions came up: do we need Cloud SQL to migrate now, and could a shared Google Drive folder do the job instead?

Q1 — Do we need Cloud SQL to migrate the app to GCP now?

✅
No — SQL can be deferred. The app, secrets, and CI/CD can all move to GCP right now while the database stays on Neon. Cloud Run simply points at the existing Neon POSTGRES_URL. Because lib/db-client.ts uses the generic pg driver, this is zero code change — the connection string just keeps pointing at Neon instead of switching to Cloud SQL.
⚠
The caveat: the database is not a one-time "MRD → PRD" migration step — it is the live persistence layer. Every One-Pager and PRD save, load, version snapshot, and rollback goes through it, and the PRD pipeline reads a saved One-Pager from it as input. So keeping Neon means the company's product data stays outside the GCP org. "Not required for now" is a deferral, not an elimination — to fully consolidate under GCP, Cloud SQL is still the endpoint (see Section E).

Q2 — Could a shared Google Drive folder replace the database?

Technically possible, but not a drop-in — and not recommended for the live data. Drive is a file store, not a query engine. The right move is to split the two roles:

❌ Drive as the database — don't

The app queries by document ID, filters by user email, reads/writes a version_history JSONB column, and does rollback lookups. To back that with Drive you'd rewrite db-client.ts and every /api/documents/* route to read/write JSON files. Worse, Drive has no transactions and no row locking — two people editing the same doc can silently clobber each other. It also breaks the clean pg swap that makes Neon→Cloud SQL easy.

✅ Drive for exported deliverables — yes

The DOCX / HTML / PDF files the generators produce (lib/document-generator.ts, lib/prd-document-generator.ts) are a natural fit for a shared Drive folder — the team can grab finished One-Pagers and PRDs without touching the app's data model. The Google Drive integration is already connected. Low risk, no rewrite.

Bottom line: migrate the app to Cloud Run on Neon today (admin's "no SQL for now" is satisfied), optionally push exports to a shared Drive folder for the team, and keep Cloud SQL as the eventual endpoint once IAM/SQL access is granted — at which point it's still a one-line connection-string change.

TL;DR — Executive Summary

  • The app uses SQL because its data is relational — 4 tables that reference each other with foreign keys, enforced status constraints, atomic transactions for version history, and ordered queries for PRD export. These are not optional features.
  • We chose Neon for speed of development — zero setup, free tier, native Vercel integration. It's standard PostgreSQL, so migrating away requires changing one environment variable.
  • Firebase cannot replace it — it's a different type of database with no foreign keys, no CHECK constraints, and no SQL. Switching would require rewriting ~800 lines of application code with new failure modes introduced.
  • Among all GCP-native options, Cloud SQL is the only correct fit — standard PostgreSQL, right price tier ($9.53/mo), fully inside the GCP org, zero code changes.
  • Per-run cost is effectively $0.00 for every feature. The entire monthly bill is a flat $9.53 for the instance being on.
  • SQL can be deferred — migrate the app to Cloud Run on the existing Neon DB now (zero code change), and keep Cloud SQL as the eventual GCP-native endpoint. Google Drive is for exported files, not for the live data — it has no transactions or queries, so using it as the database would mean an ~800-line rewrite with new failure modes.
