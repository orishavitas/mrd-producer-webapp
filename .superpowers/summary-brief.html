1 What we built
Two tools, one shared stack.
📄
One-Pager Generator — A structured product spec form. The user fills it out, AI expands the text, competitors are scraped automatically, and the result is saved, versioned, and exportable as Word/PDF. Admins can roll back to any past version.
📋
PRD Producer — Takes a saved One-Pager and runs it through a 4-step AI pipeline to produce a full Product Requirements Document. The user reviews and edits the outline halfway through (human gate), then approves it. Output is a structured PRD, exportable as Word/HTML.
🔗
The dependency: PRD reads a saved One-Pager from the database as its starting point. Both tools share the same login system, database, and AI layer.
2 The 6 tech layers — what each one does
Remove any one of these and something breaks. Here's what each piece actually does in plain terms.
🚀
Vercel / Cloud Run — the host. The platform that runs the app. Vercel is the current host; Cloud Run (Google) is the migration target. Both execute server-side code, serve pages to browsers, and run API functions. A static host (GitHub Pages) cannot run this app — it needs a real server for things like database queries and AI calls.
🔐
Google OAuth + NextAuth — the login system. When a user clicks "Sign in with Google," Google verifies who they are and sends the app a token. NextAuth turns that token into a session cookie. Every document save and every API call is tied to the user's email — this is how the app knows whose documents to show, and who is allowed to use PRD Producer (allowlist-gated).
🗄
Postgres (Neon / Cloud SQL) — the database. Stores everything that needs to survive a browser refresh: saved One-Pagers, version history, the PRD pipeline's in-progress state, completed PRD documents, and AI-generated embeddings for future search. This is the current migration blocker. See Section 4 for the full breakdown.
🤖
Gemini + OpenAI — the AI engine. Gemini (Google) is the primary AI. It handles text expansion, competitor analysis, feature suggestions, and all 4 PRD pipeline agents. OpenAI is the automatic fallback — if Gemini fails, it takes over. If both are removed, the AI features stop but the save/load/export still works.
📁
Document export layer — the file generator. Converts in-memory document state into downloadable Word files and print-ready HTML. Runs server-side because it needs to read the Compulocks logo from disk and embed it into the file. Reads the finished content from the database before generating the file.
🖥
React + CSS — the UI. The interactive form, the live preview panel, the pipeline progress screen. All styling uses named color variables from the Compulocks brand token system — no hardcoded colors anywhere. This layer has no external dependencies beyond what's already in the repo.
3 The current blocker
One missing IAM permission is preventing the full GCP migration.
🔴
What's blocked: Creating a Cloud SQL (Google's managed Postgres) instance inside the r-and-d-489319 GCP project. The app and all its other infrastructure is ready to migrate. The database is the only remaining piece.
🔑
What's needed: A GCP org admin grants two IAM roles on the project: roles/cloudsql.admin (to create the database instance) and roles/cloudsql.client (for the app to connect to it). That's the entire ask. Step-by-step guide for the admin: .superpowers/gcp-roles-guide.html.
⚠
Why IT objects to Neon: Neon (the current database host) runs on AWS, outside Google's cloud. IT wants all company data inside the GCP org. That's a valid policy — and Cloud SQL is exactly the solution. Neon is a viable interim step while waiting for IAM, but it doesn't satisfy the data-residency requirement.
4 The 3 SQL options — what each costs
There are only three realistic paths. Here they are with no padding.
Option A
Cloud SQL (Google)
  • IT-approved — data stays inside GCP
  • Zero code changes — one env var
  • $9.53/month flat (f1-micro)
  • Every feature works
  • Blocked on IAM — needs org admin action
Option B
Keep Neon (interim)
  • Works today — no IAM needed
  • Zero code changes
  • Free tier
  • Every feature works
  • Data stays outside GCP (IT concern remains)
Option C
Drop SQL entirely
  • No database cost
  • Removes IT concern
  • Breaks saving, loading, sharing documents
  • Breaks the entire PRD pipeline
  • Breaks version history and rollback
💡
Recommended path: Option B now (migrate app to Cloud Run on Neon, unblocked today), then Option A as soon as the IAM roles are granted (flip one env var, full GCP consolidation). Option C is not viable without rebuilding the product from scratch.
5 What "drop SQL" actually means — feature by feature
For anyone who needs to understand the real cost of Option C before making a call.

Save & load documents 🔴 Gone 🔴 Gone Every browser refresh wipes all work. Nothing persists between sessions.
Documents dashboard 🔴 Gone 🔴 Gone No saved documents to list. The main screen after login is empty.
Version history & rollback 🔴 Gone N/A All 20 version snapshots live in a database column. No database, no history.

⛔
Bottom line on Option C: Dropping SQL turns both tools into single-session scratch pads that forget everything the moment the tab is closed. The PRD tool stops working entirely — its core mechanism (passing state between two server calls) requires a persistent store by design. The only features that survive are AI text expansion and competitor scraping — the least differentiated parts of the product. Rebuilding without SQL would take an estimated 800+ lines of rewrite and introduce a new class of data-consistency problems.

The one-paragraph version

  • The app is a Next.js product with two tools (One-Pager + PRD) that share login, database, and AI. Both are feature-complete and live on Vercel today.
  • The GCP migration is mostly done — app, Docker, CI/CD are ready. The only remaining piece is the database: Neon (current, working, outside GCP) needs to move to Cloud SQL (Google-native, $9.53/mo).
  • The blocker is a single IAM permission. One org admin action — grant cloudsql.admin + cloudsql.client — unlocks everything. A guide for the admin is in gcp-roles-guide.html.
  • Dropping SQL entirely is not a viable alternative. It breaks document saving, the PRD pipeline, version history, and export — the core value of both tools. The features that survive without SQL are the ones anyone could build in a weekend.
  • Google Drive can't replace the database. It has no queries, no locking, and no transactions. It belongs as a destination for finished exports, not as the live data store.
