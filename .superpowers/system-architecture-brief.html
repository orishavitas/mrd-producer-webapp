System Overview — What Both Tools Do
Two production tools that share the same infrastructure. Understanding their overlap is key to understanding why every layer exists.

One-Pager Generator Live

A structured product spec generator. The user fills a 7-section form (product description, paint/logo, features, competitors, reference photos, etc.). AI expands freeform text, scrapes competitor sites, and suggests features. The result is versioned, saveable, publishable, and exportable as DOCX/HTML/PDF. Admins can roll back to any snapshot.

Core user loop: Fill → Save Draft → Publish → Export → (Admin: Rollback)

PRD Producer Alpha / Allowlist

A 4-agent pipeline that transforms a saved One-Pager into a full Product Requirements Document. The user selects a completed One-Pager, watches Agents 1–2 run, reviews and optionally edits the PRD skeleton at a human gate, then Agents 3–4 write and QA-score the full document. Export as DOCX or HTML.

Core user loop: Pick One-Pager → Watch pipeline → Review skeleton → Approve → Export PRD

🔗
The dependency chain: PRD Producer reads a saved One-Pager from the database as its starting point. This means both tools share the same database, auth system, and hosting. A change to any shared layer affects both. This is the single most important fact about the system architecture.
Shared infrastructure (used by both tools):

🔐 Auth

Google OAuth → NextAuth. Every save, load, and export is tied to a user email.

🗄 Database

Neon Postgres. Documents, versions, PRD pipeline runs, embeddings.

🤖 AI

Gemini (primary) + OpenAI fallback. All generation, analysis, and QA.

🚀 Hosting

Vercel. Next.js SSR, API routes, serverless functions, CDN.

B
Tech Layer Map — Every Piece Explained
Six distinct layers. Each has a specific role. Remove or replace any one and here is exactly what breaks.
Layer 1 — Hosting & Runtime

Vercel + Next.js App Router

What it does: Hosts the entire application. Vercel compiles the Next.js code, serves SSR pages from edge CDN nodes, runs API route handlers as serverless functions, and handles environment variable injection at deploy time. The App Router provides server components (no JS sent to browser for read-only content), client components (interactive form state), and server actions (direct DB mutations without a separate API call).

Why it's load-bearing: The next.config.js output:'standalone' bundle is built specifically for this runtime. API routes like /api/pipeline/prd/start use maxDuration: 120 — a Vercel-specific configuration for long-running streaming responses. The SSR rendering of page.tsx server components (e.g. reading isAdmin before sending HTML) only works because Vercel executes server code on every request. A static host (GitHub Pages, Netlify static) cannot run this app.

What breaks without it: Every API route, server component, server action, and streaming function stops working. The app becomes a blank page.

Layer 2 — Authentication

Google OAuth → NextAuth.js → Feature Gate

What it does: Three sub-components working together. (1) Google OAuth — the user clicks "Sign in with Google", Google verifies their identity and returns their email. (2) NextAuth.js (lib/auth.ts) — receives the Google token, creates a signed JWT session cookie, and exposes auth() which every API route calls to verify who is making the request. (3) Feature Gate (lib/feature-gate.ts) — checks the user's email against config/allowlist.txt (or the ALLOWED_RD_EMAILS env var) and returns a set of allowed feature keys. The dashboard only shows tools the user is allowed to see.

Why it's load-bearing: Every document save, load, version, and pipeline run is keyed to session.user.email. Without auth, anyone could read or overwrite anyone's documents. The PRD pipeline uses the email to check ownership before allowing approval or export. The admin rollback feature checks lib/admin.ts → isAdmin(email).

On GCP (stub mode): BYPASS_AUTH=true skips OAuth entirely and returns a hardcoded stub session (ori@compulocks.com). This is intentional for the Cloud Run migration phase — restore real OAuth once IAP or a custom domain is set up.

Layer 3 — Database

Neon Postgres — 5 tables, 1 extension

What it does: Stores everything that persists between sessions. Five tables: documents (One-Pager content + version history), document_embeddings (768-dim pgvector embeddings for semantic search), pipeline_runs (PRD pipeline state machine), prd_documents (completed PRD metadata + QA score), prd_frames (12 individual PRD section texts, ordered). Also stores version and version_history (JSONB array of up to 20 snapshots) on documents for the versioning + rollback system.

The pgvector extension (CREATE EXTENSION IF NOT EXISTS vector) enables the 768-dimension vector column for semantic search. Neon enables this automatically; Cloud SQL requires a flag in the GCP console; self-hosted Postgres requires manual installation.

Why it's load-bearing: The PRD pipeline is a state machine across multiple HTTP requests. Status transitions (running → awaiting_approval → approved → completed) are enforced by a SQL CHECK constraint. The skeleton_json JSONB column persists the AI-generated skeleton between Agent 2 and the human-gate approval. Without the database, the pipeline state is lost between requests. One-Pager versioning and rollback are entirely JSONB-in-Postgres — no file system, no external store.

The driver: lib/db-client.ts uses the generic pg npm package with a Pool (max 10 connections). The connection string is POSTGRES_URL. This works with Neon, Cloud SQL, Supabase, Railway, or a local Postgres — no code changes needed when switching hosts.

Layer 4 — AI Provider Chain

Gemini (primary) + OpenAI (fallback) + Provider Chain

What it does: lib/providers/provider-chain.ts is a priority-ordered fallback system. Gemini is priority 0 (primary); OpenAI is priority 1 (fallback). When an AI call is made, the chain tries Gemini first. If Gemini fails (quota, error, timeout), it automatically retries with OpenAI. The chain also differentiates between regular text generation and search-grounded generation — Gemini supports real-time web search via its grounding API; OpenAI does not, so search queries gracefully fall back to ungrounded text generation.

What it powers: (One-Pager) text expansion, feature suggestion, competitor scraping analysis, embedding generation; (PRD) all 4 agents — analyst normalises the One-Pager, architect generates the skeleton, writer writes 8 PRD sections, QA scores and critiques. Embeddings specifically use text-embedding-004 (Gemini) to produce 768-dim vectors stored in pgvector.

Why both keys matter: Remove GOOGLE_API_KEY and the primary chain breaks — embeddings break completely (OpenAI uses 1536-dim, incompatible with the existing pgvector index). Remove OPENAI_API_KEY and the fallback is gone — a Gemini outage takes the whole tool down.

Layer 5 — Document Export

docx + HTML/CSS → DOCX / PDF / HTML

What it does: lib/document-generator.ts (One-Pager) and lib/prd-document-generator.ts (PRD) convert in-memory document state into downloadable files. DOCX uses the docx npm package — building Word-compatible XML in memory with Arial font, US Letter margins, Compulocks logo as a right-aligned ImageRun in the header. HTML export produces a print-ready page with embedded base64 logo (no external URLs needed). PDF is generated by the browser's print dialog from the HTML export. The export API routes (/api/one-pager/export, /api/pipeline/prd/[run_id]/export) run server-side so the user never needs Word installed.

Why it's serverside: Reading the Compulocks logo from disk (fs.readFileSync), base64-encoding it, and embedding it in HTML requires Node.js — this cannot run in a browser. This is why export routes are Next.js API routes, not client-side code.

Layer 6 — Frontend State & UI

React 18 + useReducer + CSS Modules + Brand Tokens

What it does: All interactive form state lives in useReducer + Context — no external state library. The One-Pager has a 350-action reducer in app/one-pager/lib/one-pager-state.ts; PRD UI state is in component-local state and polling hooks. CSS Modules scope styles per component; all colors and spacing reference CSS custom properties from styles/tokens/compulocks.css and app/one-pager/one-pager-tokens.css — no hardcoded hex values anywhere. The design system uses Barlow / Barlow Condensed fonts loaded from Google Fonts.

The server/client split: page.tsx files are server components — they run on the server, read auth and admin status, then pass those as props to the *Client.tsx client entry point. This means the user never sees a flash of wrong state (e.g. admin controls appearing briefly for non-admins). All hooks, event handlers, and reducers live in client components only.

A 4-agent pipeline split across two HTTP requests with a human gate in the middle. This is why the database is non-negotiable for the PRD tool.

⚠
Why the database is mandatory for PRD (not optional): The pipeline spans two separate HTTP requests with a human action in between. Phase 1 (/api/pipeline/prd/start, maxDuration 120s) writes the skeleton to pipeline_runs.skeleton_json and sets status = 'awaiting_approval'. The user's browser polls /api/pipeline/prd/[run_id]/status to detect this state. The human gate approval hits /api/pipeline/prd/[run_id]/approve. Phase 2 (/api/pipeline/prd/[run_id]/resume, maxDuration 300s) reads the skeleton back from the database and continues. Without the database, the skeleton generated in Phase 1 is gone — Phase 2 has nothing to work with.

DB tables touched per pipeline run

pipeline_runs — created at start; status updated at every phase transition; skeleton_json written by Agent 2, read by Agent 3.

prd_documents — created after Agent 4 completes; stores product name, QA score (0–100), and QA suggestions.

prd_frames — one row per section (8 rows); section_order ensures consistent export ordering.

documents — read-only during PRD; the One-Pager source content is fetched here by Agent 1.

Streaming + heartbeat

Both /start and /resume return NDJSON streams (newline-delimited JSON events). The browser reads the stream and updates the PipelineOverlay UI in real time.

The withHeartbeat() wrapper in the resume route sends a keep-alive ping every 5 seconds so Vercel's 300s timeout is not triggered prematurely by silence. Without this, long AI generation calls would cause the connection to drop mid-stream.

Export (/export?format=docx|html) is a separate synchronous GET — it reads the saved frames from the DB and returns a file download.

G
Plain-English Glossary — What Every Tech Term Means
No assumed knowledge. Every piece of technology in this document explained in one paragraph, as if you've never heard of it.

Next.js

A framework built on top of React (the UI library made by Meta) that adds the server side. Without Next.js you'd have a website that only runs in the browser — it can't keep secrets, can't talk to a database, and can't do anything that requires a real server. Next.js runs server code on Vercel so that things like "check if this user is logged in" or "read from the database" happen before the page is sent to the browser. It's the backbone the entire app is built on.

Vercel

A cloud hosting platform specifically designed for Next.js apps. Think of it like a smart landlord for the app: it takes the code, compiles it, distributes it to servers around the world, and automatically updates everything when new code is pushed to GitHub. It also handles environment variables (secret keys the app needs), manages function timeouts, and provides a CDN so pages load fast everywhere. The app works on Vercel without any server configuration — it's zero-ops hosting.

Google Cloud Run

Google's equivalent to Vercel — a service that runs containerized applications without managing servers. Instead of deploying code directly, Cloud Run runs a Docker container (a self-contained box with the app and everything it needs). The app already has a Dockerfile ready. Cloud Run is what the GCP migration targets: the app moves from Vercel's infrastructure to Google's, staying inside the r-and-d-489319 GCP project your IT team controls.

Docker / Dockerfile

A Docker container is a self-contained package that includes the app, its dependencies, and its runtime — so it runs identically on any machine or cloud. A Dockerfile is the recipe for building that container. The app already has one (Dockerfile in the root), which is why moving from Vercel to Cloud Run requires zero code changes — the same container works on both.

PostgreSQL (Postgres)

A database — software that stores data persistently so it survives server restarts, can be queried efficiently, and handles multiple users at once safely. Postgres specifically is a relational database: data lives in tables (like spreadsheets), rows in one table can reference rows in another (foreign keys), and you can enforce rules like "status must be one of these five values" at the database level. It's the industry standard for web applications that need structured, reliable data storage.

Neon

Neon is a company that hosts Postgres databases as a managed cloud service — so you get a real Postgres database without running or maintaining a server yourself. It has a generous free tier, integrates natively with Vercel, and enabled us to get a working database in minutes during development. The data lives on Neon's infrastructure (AWS us-east-1), which is outside Google's cloud — that's the IT concern. From the app's perspective, Neon is identical to any other Postgres database.

Google Cloud SQL

Google's managed Postgres service — the same as Neon in concept, but running inside Google Cloud instead of AWS. It costs ~$9.53/month for the smallest instance. Since it lives in the same GCP project as Cloud Run, data never leaves Google's network. It's the IT-approved long-term database target. The only reason we haven't migrated yet: the GCP org admin needs to grant SQL-specific IAM roles before the instance can be created.

IAM (Identity and Access Management)

Google Cloud's permission system. Every action in GCP — creating a database, deploying an app, reading a secret — requires an IAM role that grants that permission. IAM roles are assigned to users or service accounts. The current blocker: ori@compulocks.com has run.admin (can manage Cloud Run) but not cloudsql.admin (can create/manage Cloud SQL instances). An org-level admin at your company needs to grant those SQL roles before the database migration can proceed.

OAuth / Google OAuth

OAuth is a standard protocol that lets users log in with an existing account (like Google) instead of creating a new username and password. When a user clicks "Sign in with Google," Google verifies their identity and sends the app a token confirming who they are. The app never sees the password — Google handles that. This is how the app knows whose documents to show and whether a user has access to PRD Producer (which is allowlist-gated).

NextAuth.js

A library that handles the plumbing between OAuth (Google's login system) and the app. It receives Google's token, creates a signed session cookie in the user's browser, and exposes an auth() function that any API route can call to find out who is making the request. Without NextAuth, every API route would have to implement its own session management, which is both complex and a security risk.

API Route / Serverless Function

An API route is a URL that the app exposes for the browser (or other services) to call — like /api/documents/[id] for saving a document. On Vercel and Cloud Run, each route runs as a serverless function: a small piece of code that spins up on demand, handles the request, and shuts down. There's no permanently running server — the platform handles scaling up and down automatically. This is why long-running operations (like the PRD pipeline's 5-minute AI write) need special timeout configuration.

NDJSON Streaming

NDJSON stands for Newline-Delimited JSON. Instead of waiting for an entire AI response to finish before sending it to the browser, streaming sends it in small chunks — one JSON object per line, as each event happens. This is how the PRD pipeline shows "Agent 1 complete… Agent 2 running…" in real time rather than a blank loading screen for 3 minutes. The browser reads the stream line by line and updates the UI as each event arrives.

Gemini (Google AI)

Google's large language model family — the AI that powers every text generation, analysis, and expansion feature in the app. The app uses gemini-2.5-flash and gemini-2.5-pro depending on task complexity. Gemini is also the source of the text-embedding-004 model used to generate vector embeddings for semantic search. The API key is GOOGLE_API_KEY. Gemini is priority 1 in the provider chain — if it's unavailable, OpenAI takes over.

OpenAI

The company behind GPT-4 and the ChatGPT API. In this app, OpenAI is the fallback AI provider — used automatically if Gemini is unavailable or returns an error. The OPENAI_API_KEY is optional but recommended. One critical caveat: OpenAI's embeddings produce 1536-dimensional vectors, while Gemini produces 768-dimensional vectors. Because the database index was built for 768 dimensions, embeddings always use Gemini — OpenAI cannot substitute for that specific function.

pgvector

A Postgres extension (add-on) that teaches Postgres to store and search high-dimensional vectors — arrays of hundreds of floating-point numbers that represent the "meaning" of text. When a One-Pager is saved, its content is sent to Gemini which returns a 768-number vector. That vector is stored in Postgres. Later, you can search for "products similar to this one" by finding vectors that are mathematically close (cosine similarity). This is how semantic search works — it finds meaning, not just matching words.

JSONB

A Postgres column type that stores JSON (structured data like {"key": "value"}) in a binary format that can be efficiently indexed and queried. The app uses JSONB for the One-Pager's content_json (the entire form state), version_history (an array of up to 20 past snapshots), and the PRD pipeline's skeleton_json (the AI-generated section strategies). It lets Postgres store flexible, nested data alongside structured relational data in the same database.

Foreign Keys

A rule in a relational database that says "this column must reference a row that actually exists in another table." For example, pipeline_runs.source_document_id is a foreign key to documents.id — you can't create a pipeline run that points to a non-existent document. This prevents orphaned data (a PRD with no source One-Pager) and ensures the database stays consistent. NoSQL databases like Firebase do not have foreign keys — you'd have to enforce this logic manually in application code.

Secret Manager

Google Cloud's service for storing sensitive values like API keys and database passwords. Instead of hardcoding POSTGRES_URL=postgres://user:pass@host/db in a config file (where it could leak), the secret is stored in Secret Manager and injected into Cloud Run at deploy time. The app never sees the raw value in logs or source code. On Vercel, the equivalent is the Vercel dashboard's Environment Variables. On GCP, Secret Manager is the right tool — it's audited, versioned, and access-controlled via IAM.

Feature Gate / Allowlist

A system that controls which users can access which tools. The app reads config/allowlist.txt — a plain text file where each line is an email address followed by which features (1–7) they're allowed to use. Feature 5 = PRD Producer. Users not on the list see the tool hidden from their dashboard. This lets the team give access to PRD to specific people during alpha testing without deploying code changes — just update the file.

CSS Modules + Design Tokens

CSS Modules are scoped stylesheets — each component's CSS only applies to that component, preventing styles from accidentally leaking into other parts of the page. Design tokens are named variables for colors and spacing (--brand-primary: #1D1F4A, --accent: #009966). Instead of hardcoding colors everywhere, every style references a token. This means changing the brand color requires editing one variable, not hundreds of files. All tokens live in styles/tokens/compulocks.css.

Option 1 — Google Cloud SQL
IT-approved · Full GCP · One env var change · ~$9.53/mo · Blocked on IAM

What you keep

Everything. Every feature in both tools works exactly as today. Full version history, rollback, PRD pipeline, embeddings, export — all intact. Data lives inside the GCP org. No code changes. One env var: POSTGRES_URL switches from Neon's TCP URL to Cloud SQL's Unix socket path.

What's blocking it

The GCP org admin needs to grant two IAM roles on r-and-d-489319:

roles/cloudsql.admin — to create the instance
roles/cloudsql.client — for the Cloud Run service account to connect

Once granted, this is a 30-minute operation. A guide for the admin is in .superpowers/gcp-roles-guide.html.

ℹ
One extra step: Cloud SQL requires enabling the pgvector database flag in the GCP console before running the schema. Otherwise CREATE EXTENSION vector fails silently and the embeddings column is not created. This is a 2-click change in the GCP console — it is not a code change.
⚠
Option 2 — Keep Neon (defer Cloud SQL)
Works today · No IAM needed · Data outside GCP · IT concern remains

What you keep

Everything. All features work. App migrates to Cloud Run now, database stays on Neon. POSTGRES_URL is unchanged. Zero code changes. Unblocks the GCP migration immediately.

What IT still has a problem with

Neon runs on AWS, outside the GCP org. Product data — saved One-Pagers, PRDs, version history — lives on a third-party service the company doesn't control. This is the IT objection. It doesn't affect functionality, but it means the "everything under GCP" goal is not met until Cloud SQL is in place.

⚠
This is a valid interim step. Migrate the app to Cloud Run on Neon now. When IAM/SQL is granted, flip the one env var to Cloud SQL and the migration is complete. No features are lost at any point in this process.

TL;DR — For the Admin

  • ✓Both tools (One-Pager + PRD) share the same 6-layer stack: hosting, auth, database, AI, export, and UI.
  • ✓The database is not a migration-only concern — it is the live persistence layer used on every save, load, version, rollback, and PRD pipeline run.
  • ✓SQL can be deferred: migrate the app to Cloud Run on the existing Neon DB today — zero code changes. Cloud SQL becomes the target once SQL IAM roles are granted.
  • ✓Google Drive cannot replace the database (no queries, no transactions, no vector search). It belongs as a destination for exported DOCX/PDF files, not as the data store.
  • ✓No free GCP alternative fits: Firebase/Firestore, BigQuery, and Bigtable are all wrong types of database for this app's relational, transactional, and vector-search requirements.
  • ✓When Cloud SQL is ready: it is a one-line env var change. Every query, schema file, and type definition in the codebase is already compatible.
